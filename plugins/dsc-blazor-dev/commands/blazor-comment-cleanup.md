# Blazor comment cleanup

DSC hard rule: code carries no comments except `///` XML doc comments and `/** */` JSDoc on types,
members and functions. The comment guard stops new ones; this command removes the ones already
there. Old comments are not harmless: agents read them as instructions, and many were left by AI
and are stale or wrong.

Scope: `$ARGUMENTS`, or the repo root when empty. Generated code is skipped by the scanner
(`obj/`, `bin/`, `Migrations/`, `*.g.cs`, `*.Designer.cs`, `<auto-generated>` files,
`wwwroot/lib/`, `*.min.js`).

## 1. Inventory

```bash
python "${CLAUDE_PLUGIN_ROOT}/tools/comment-guard/comment_guard.py" scan <scope> --json > "<scratchpad>/comments.json"
```

Show the user one block: total comments, files, the 5 files with the most, and how many look like
commented-out code. Branch: follow the git branch policy (stay on the current branch unless the
user agrees to a new one). Then proceed: the user asked for the cleanup by running this command.

## 2. Batches

Split the files into batches of about 15 files or 300 comments, one project or feature folder per
batch where possible. Batches touch disjoint files, so run up to 3 `blazor-dev:blazor-developer`
tasks in parallel. The main thread never edits C#/Razor itself (main-thread guard).

Brief for each task (fill in the file list and the comment list for those files):

> Remove the comments listed below from these files. DSC hard rule: no comments in code except
> `///` XML doc comments and `/** */` JSDoc. Do not commit and do not create branches: other
> batches run in the same working tree. For each comment decide:
> 1. **Restates the code, section header, `// Arrange` / `// Act` / `// Assert` label, ticket
>    reference, TODO with no open work, commented-out code or markup** → delete it.
> 2. **Documentation** (what a type or method is for, who calls it, an ordering or transaction
>    constraint, an edge case) → move it into the enclosing member's or type's `///` doc comment
>    (`<summary>`, or `<remarks>` for the rest), then delete the inline comment. Add the doc
>    comment if the member has none. In Razor, move it to the component's code-behind class doc
>    comment.
> 3. **The code can say it** → rename a local or a private/internal member, extract a small
>    private method whose name states the intent, introduce a named constant; in Razor, extract
>    a child component whose name is the label. Never rename anything public, any API route,
>    DTO property, stored-procedure name or anything another project consumes, and never change
>    behaviour.
> 4. **Defends a choice** ("we do X because Y", "workaround", "hack", "not ideal") → apply 2 or 3,
>    and also add the choice to the Doubts list in your report with file:line and one sentence.
> 5. **Open work** (TODO/FIXME that still applies) → delete it and add it to the Open work list.
>
> Run `dotnet build` and `dotnet test` for the affected projects after the batch. The diff must
> contain only comment removals, doc-comment additions and the renames/extractions from 3; no
> logic change. Return: files changed, comments removed, moved to doc comments,
> renamed/extracted, the Doubts list and the Open work list, and the build and test result.

## 3. Verify

Re-run the scan on the scope: it must report 0. Any remaining hit is either a missed comment
(send it back) or a scanner false positive (a `//` inside an unusual string literal or markup
text): report those to the user by file:line, never wrap them in a suppression.

Then commit on the current branch, one commit per project or app: `refactor: remove
non-documentation comments (DSC no-comments rule)`.

## 4. Report to the user

- comments removed, files touched, build and test result;
- moved into doc comments: count;
- **Doubts**: the choices comments were defending, file:line + one sentence each. These are the
  spots where an agent was not sure. Offer to open a triage on any of them;
- **Open work**: the TODOs that still applied, as a list the user can turn into Issues;
- the commit(s) made. Push only when the user says so.
